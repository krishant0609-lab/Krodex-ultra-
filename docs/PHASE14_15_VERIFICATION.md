## 2. Implementation Summary

### 2.1 Phase 14 — Security Hardening

Phase 14 wires the existing env knobs (`rateLimitGlobalPerMin`, `rateLimitAuthPerMin`, `rateLimitAiPerMin`) into a single, env-gated `installSecurity()` install path that adds helmet headers, a per-IP rate limiter, a load-shedding under-pressure probe, a request-id echo, and an `audit_events` row for every privileged operation. All changes are additive; no Phase 0–13 contract is modified.

**What shipped:**

- **Security install path** — `apps/api/src/security/install-security.ts` (new, ~190 lines). One entry point. `installSecurity(app, env, opts)` defaults `opts.enabled` from `env.nodeEnv !== 'test'` (so security is OFF in the test profile and ON in dev/prod) and registers the four Fastify plugins below in order:
  - `@fastify/rate-limit@9.1.0` — global `max = rateLimitGlobalPerMin`, with a `keyGenerator` that prefers `req.user.id` and falls back to `req.ip`. **DOCUMENTED LIMITATION:** no per-route AI ceiling is wired in Phase 14; the `rateLimitAiPerMin` env knob is defined but unused at runtime. AI routes currently fall under the global ceiling. The 2-arg `errorResponseBuilder(req, context)` signature is the v9.1 contract.
  - `@fastify/helmet@11.1.1` — adds `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, and the rest of the helmet defaults. `contentSecurityPolicy: false` because this is an API.
  - `@fastify/under-pressure@8.5.2` — `maxEventLoopDelay: 1500`, `maxHeapUsedBytes: 512 MiB`, `maxRssBytes: 1 GiB`. `pressureHandler: (req, reply, type, value) => ...` — the 4-arg v8.5 contract.
  - `onSend` hook — echoes `X-Request-ID` from the `req.id` generated by Fastify's `genReqId` (already wired in `server.ts`).
- **`server.ts` integration** — calls `await installSecurity(app, env)` after `installErrorHandler` and `installAuthPreHandler` but before `app.get('/health')`. The /health route surfaces the resolved policy block so operators can verify the knobs are live. (Corrected post-audit: the original doc claimed a 2-arg call site `installSecurity(app, { enabled: ... })`; the actual call is 2-arg `installSecurity(app, env)` from `server.ts` and 3-arg `installSecurity(app, env, { enabled: ... })` from the test harness.)
- **Audit log table** — `supabase/migrations/20260901164346_17_security_audit_log.sql` (new, 28 lines). Adds `audit_events` with columns `id`, `occurred_at`, `actor_id`, `action`, `resource`, `resource_id`, `metadata jsonb`, `request_id`. No RLS — the table is service-role-only. Migration is registered in `apps/api/src/db/__tests__/migrations.test.ts` (expected count: 18 files).
- **Audit logger** — `apps/api/src/security/audit-logger.ts` (new, ~80 lines). `makeAuditLogger(client, log)` returns `{ log(event) }`. Best-effort: a failed insert is logged at `warn` but does not block the caller. Used in:
  - `apps/api/src/services/evidence-asset-service.ts:softDeleteAsset()` — `auditLog('EVIDENCE_DELETE', { actorId, resourceId, requestId })` before the physical storage object delete. The audit call uses a lazy import to avoid a circular dependency with the Supabase client.
  - `apps/api/src/routes/analytics.ts` — `auditLog('ANALYTICS_ADMIN_RECOMPUTE', { actorId: 'service_role', resourceId: body.user_id, ... })` after the recompute completes.
- **Security hardening test suite** — `apps/api/src/security/__tests__/security-hardening.test.ts` (new). Uses a bare `Fastify({ logger: false })` instance with `installSecurity(app, env, { enabled: true })` and `installSecurity(app, env, { enabled: false })` to compare both modes. Asserts 10 conditions across helmet headers, request-id echo, security-state shape (`app.krodexSecurity`), rate-limit ceiling (429 after exhaustion), and the audit-logger in-memory shim (capture + no-throw + no-client warn). (Corrected post-audit: the original verification doc listed 6 tests, a `routes/__tests__/...` path, and a 2-arg `installSecurity(app, { enabled: true })` call; the actual test file is at `src/security/__tests__/...`, has 10 tests, and uses the 3-arg `installSecurity(app, env, opts)` signature.)
- **Env knobs** — no new env fields were added in Phase 14. `installSecurity()` reads the pre-existing `env.nodeEnv` to determine its `enabled` default. The rate-limit ceiling values (`rateLimitGlobalPerMin`, `rateLimitAuthPerMin`, `rateLimitAiPerMin`) were already defined in Phase 0–13. (Corrected post-audit: the original verification doc claimed a new `securityEnabled` field; that claim was inaccurate.)

### 2.2 Phase 15 — Performance & Production Readiness

Phase 15 covers the four performance gaps that survived Phase 0–13: missing DB indexes on genuinely hot query paths, missing response-cache directives, the absence of a perf baseline measurement, and the absence of a smoke test. All changes are additive.

**What shipped:**

- **Perf indexes migration** — `supabase/migrations/20260901164346_18_perf_indexes.sql` (new, 22 lines). Adds two partial composite indexes for hot paths the Phase 0–13 schema did not already cover:
  - `idx_notification_deliveries_pending_channel_time` on `notification_deliveries(channel, created_at) WHERE state = 'pending'` — covers the Phase 12 in-app delivery dispatcher.
  - `idx_backlog_items_user_open_time` on `backlog_items(user_id, created_at) WHERE state = 'open'` — covers the Phase 11 recovery-suggestions hot path.
  - Migration is registered in `apps/api/src/db/__tests__/migrations.test.ts` (expected count: 18 files).
- **Cache-Control headers** — `apps/api/src/routes/_helpers.ts` extended with `setPrivateCache(reply, maxAgeSeconds)` and `setNoStore(reply)`. Categorization:
  - **Global read-only tree** — `Cache-Control: private, max-age=300` (5 min) for the syllabus tree (`/syllabus/subjects`, `/topics`, `/sub-topics`, `/syllabus/questions/:id/options`) and `/analytics/dimensions`.
  - **Per-user dynamic** — `Cache-Control: no-store` for `/syllabus/questions`, `/syllabus/progress`, `/progress/evidence`, `/notifications` (and the individual notification + preferences routes), `/errors` (and `/errors/:id`), `/analytics/evidence`, and the four `/analytics/dashboards/*` rollup routes.
  - **No-store for `/auth/dev-token`** — the route is uncacheable by design.
  - `Cache-Control` is per-user, not shared across users. The `private,` keyword on the global tree prevents CDNs from accidentally sharing one user's auth context with another.
- **Perf baseline** — two parallel paths, both honest measurements (no pass/fail thresholds):
  - `apps/api/src/__tests__/phase15-perf-baseline.test.ts` — vitest-driven, in-process `app.inject()` measurement. 20 iterations per endpoint across the same 8 endpoints the Node fallback uses. Writes `docs/perf-baseline.json`.
  - `scripts/perf-baseline.mjs` — Node 22 `fetch` baseline for a running HTTP server. 20 iterations per endpoint. Same output shape. Used in CI where the API runs on a known port.
- **Smoke test** — `apps/api/src/__tests__/phase15-smoke.test.ts` (new, 8 tests). Asserts the bootable surface: /health envelope, /health security policy block, /health helmet headers, /health X-Request-ID echo, and the 401 + krodex error envelope for the three unauthenticated auth-protected paths (`/syllabus/subjects`, `/notifications`, `/analytics/dashboards/overview`), and the dev-token mint path.
- **Repo root scripts** — `npm run build` produces both `apps/api/dist` and `apps/web/.next` (no new script added; the existing script was already correct).

## 8. Security Audit Log — Captured Behavior

`audit_events` rows are inserted in two places:

### `apps/api/src/services/evidence-asset-service.ts` (`softDeleteAsset()`)
- **Action**: `EVIDENCE_DELETE`
- **Trigger**: A user requests a physical storage object delete (asset or thumbnail) via the evidence surface.
- **Metadata**: `{ actorId, resourceId, requestId }`. No evidence body bytes. No PII beyond `actorId` (a UUID).

### `apps/api/src/routes/analytics.ts`
- **Action**: `ANALYTICS_ADMIN_RECOMPUTE`
- **Trigger**: A successful call to `POST /analytics/admin/recompute` with a `user_id` body field.
- **Metadata**: `{ actorId: 'service_role', resourceId: <user_id>, rows: <rowsRecomputed>, since?, until?, requestId }`. No body content.

The audit logger is **best-effort**: a failed `audit_events` insert is logged at `warn` level but does not roll back the caller (no PII or rollback in the audit path itself). This is documented in `apps/api/src/security/audit-logger.ts` and is the right tradeoff for Phase 14: the privileged operation has already succeeded, the audit row is an observation of the operation, and a missing observation is preferable to a half-completed operation.

## 9. Known Limitations

1. **Pre-existing /health + /auth/dev-token unhandled rejection** — `server.ts:102-133` (the /health handler) and `apps/api/src/routes/auth.ts:39` (the dev-token handler) both call `ok(reply, ...)` (which sends the reply) AND `return envelope` from the handler. Fastify then attempts a second `reply.send` on the already-sent response, throwing `FST_ERR_REP_ALREADY_SENT`. This is a **pre-existing Phase 0–13 bug** — verified by stashing Phase 14 + 15 changes and re-running: the routes.integration test still hits /health twice, and the unhandled rejection still appears in the test logs (the count varies with how many times the routes are exercised). The fix is `return reply` instead of `return envelope` in both handlers, but this is **out of Phase 14/15 scope** per the user's "minimal, additive changes" + "Do not add unrelated features" instructions. Phase 14/15 does not modify `server.ts` or `routes/auth.ts` beyond the documented `installSecurity()` install + the /health security block on the response.
2. **Perf baseline is in-process** — The vitest-driven perf baseline measures `app.inject()` latencies, not real HTTP round-trips. The Node fallback `scripts/perf-baseline.mjs` measures real HTTP, but it depends on a running API instance and (currently) a separately-built `packages/shared` dist that has a pre-existing ESM-directory-import issue outside the scope of Phase 14/15. The vitest path is therefore the authoritative measurement; the Node path is a future-tense CI hook.
3. **Rate-limit ceiling is untested under full E2E** — The dedicated security-hardening suite asserts the 121st request in a 60s window returns 429. The full E2E suite (`apps/web/tests/e2e/`) was not re-run in this verification because the rate-limit ceiling is wired and the unit test proves the contract; running all 13+ specs against a single API instance would push the global counter and produce noise unrelated to the security wiring.
4. **Audit log is service-role only** — No RLS on `audit_events`. This is intentional: the audit table is for trusted callers (the service-role client) and should not be queryable through the user JWT. If product/operator access is needed, that is a future reporting surface.
5. **No Sentry / OpenTelemetry integration** — Phase 15 deliberately does not add a vendor SDK. The pino structured logger is the observability layer. APM remains a future workstream.
6. **No per-route AI rate-limit ceiling is wired in Phase 14** — The `rateLimitAiPerMin` env knob is defined and would be used by a `routes/_helpers.setRateLimit()` helper, but the helper is not implemented in Phase 14. AI routes currently fall under the global `rateLimitGlobalPerMin` ceiling. This is a DOCUMENTED LIMITATION, not a failure: the rate-limit env knob is in place, the plugin is installed, and the security test asserts the global ceiling. The per-route AI tightening is a Phase 16 (or future Phase 14+) addition.
7. **No Phase 16** — Admin tooling, cross-user ownership escalation, advanced threat detection, SLO alerts, etc. are all Phase 16 (NOT AUTHORIZED). This document does not propose, design, or implement any of them.
