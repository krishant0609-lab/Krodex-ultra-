1. Product Vision and Product Contract

KRODEX is a learning operating system whose central job is to turn study activity into a durable, explainable evidence
loop. The application must feel like one system rather than a collection of attractive screens.

The core loop

Plan  Study  Attempt  Submit  Capture error evidence  Classify  Review  Retest  Resolve or Reopen 
Adapt. Every stage produces durable state that downstream pages can read.

What makes KRODEX different

 · Errors are first-class records, not temporary warnings.
 · An incorrect test answer can automatically create an evidence-backed error without manual retyping.
 · Reviews are tied to errors and produce explicit outcomes.
 · Resolution requires qualifying evidence; opening or reading an error never counts as resolution.
 · Dashboard, Planner, Errors, Reviews, Tests, Insights and Notifications are projections of shared state.

Product contract

  If a student makes a mistake, KRODEX must remember what happened, preserve the learning context, connect
  it to the syllabus, create correction work, surface that work, evaluate the correction, and update the student's
  learning picture without requiring manual copying between modules.

Non-goals

 · Not a social network.
 · Not a decorative streak counter.
 · Not an AI-only tutoring wrapper.
 · Not a static timetable.
 · Not a collection of independent mock pages.
 · Not a system that silently edits learning history.

2. Users, Goals and Success Criteria

The primary user is a student preparing for an examination with a defined syllabus and a recurring need to practice,
diagnose mistakes and revise weak areas.

Primary user jobs

Job                                          Trigger                              Expected result

Know what to study                           Beginning a session                  One or more actionable priorities

Practice                                     Need performance evidence            A relevant test

Understand a mistake                         Incorrect answer                     Evidence + category + explanation

Correct a mistake                            Review due                           Fresh verification

Track progress                               Any time                             Traceable performance picture

Recover missed work                          Task/review overdue                  Reschedule without erasing history

Success criteria

· A new user can reach the first test without needing undocumented setup.

· An incorrect answer becomes a visible error record after submission.

· The error record contains source context and automatic question evidence.

· A review can be started directly from the error.

· A failed review keeps the error active and adds new evidence.

· A qualifying successful review can resolve the error according to policy.

· A later recurrence can reopen a previously resolved error.

· Refreshing any major page produces the same underlying truth.

Release gates

Persistence                                                       Refresh/navigation does not lose durable state

Recovery                                                          Failures do not create duplicate or contradictory records

Evidence                                                          Every derived claim can be traced to source data

4. Dashboard -- Complete Page Requirements

Dashboard is the operational home. It should prioritize action and evidence instead of maximizing the number of cards.

Page anatomy

Region                                       Content                                   Interaction

Header                                       Today/date/context                        Change context where supported

Action strip                                 Start test / review / study               Immediate launch

Today queue                                  Due tasks, reviews, tests                 Open/complete/start

Learning pulse                               Recent attempts, accuracy, active errors  Open analytics

Priority weaknesses                          Evidence-backed topics                    Drill into topic/errors

Recent activity                              Domain event timeline                     Open source record

Upcoming                                     Future reviews/tasks                      Open planner

Priority logic

v1 priority is deterministic and explainable. Candidate work can be ranked using unresolved state, review due status,
recurrence count, recency of failure and explicitly configured syllabus importance. The UI should expose a short reason
such as '3 recent errors in this topic' rather than an opaque score.

First-use state

When there is no learning evidence, Dashboard should become a guided setup page: profile  syllabus  first task 
first test. It should not overwhelm the user with empty charts.

Dashboard data contract

 · Counts are derived from durable records.
 · Activity comes from real domain events.
 · Weaknesses include supporting evidence counts.
 · Recommendations include a reason and destination.
 · Refreshing after a mutation must converge to current state.

5. Dashboard -- State, Loading, Empty and Failure Behavior

A real dashboard must define every state, not only the populated state.

Loading state

· Show structural skeletons matching final card dimensions.

· Do not show stale zeroes as though they were real values.

· Preserve page title and navigation while data loads.

· Long-running analytics can load progressively.

Empty state

Explain why the dashboard is empty and give the next setup action. Example sequence: 'Your learning history is empty'
 'Add your syllabus'  'Create your first test'.

Partial-data state

If the student has a syllabus but no tests, show syllabus coverage and the next action rather than pretending performance
is available.

Error state

A failed dashboard request must identify that the data could not be loaded, provide retry, and preserve navigation. It must
never replace a failed request with invented placeholder metrics.

Interconnection examples

Submit test                                                  Recent activity + performance update

Incorrect answer                                             Active error/priority may update

Complete review                                              Due/open counts change

7. Syllabus -- Create, Edit, Reorder and Archive Flows

The syllabus editor must protect hierarchy integrity and preserve historical meaning.

Create flow

Select parent (unless creating a Subject), enter name, optionally add description, validate duplicate sibling names
according to policy, save, then return to the node context.

Edit flow

· Inline edit or modal edit may be used.

· Save must preserve node ID.

· Existing questions/errors/tasks remain linked.

· Validation prevents empty names.

· Cancel must not mutate state.

Reorder flow

Sibling ordering is explicit and deterministic. Reordering must not change parent relationships. Existing deep links remain
valid.

Archive flow

Archive requires confirmation because it changes future selection availability. Historical records remain visible in relevant
detail pages.

Edge cases

Case                                              Expected behavior

Duplicate name                                    Warn or prevent according to defined uniqueness policy

Empty name                                        Block save

Archived parent                                   Prevent new active children unless explicitly restored

Node with history                                 Archive, do not hard-delete

Concurrent edit                                   Detect conflict or refresh before overwrite

12. Special Feature -- Automatic Error Capture and
Screenshot

This is the defining product workflow requested for KRODEX. It must be treated as a P0 feature and designed as a
transaction, not as a decorative overlay.

Trigger

When an analyzed answer is incorrect, the system creates an ErrorEvidence record automatically. The student may also
explicitly log an error during an attempt, but automatic capture is the default path after a confirmed incorrect answer.

Evidence captured

Evidence                                     Requirement

Question snapshot                            Capture the in-app question context

Student response                             Preserve exact selected/entered answer

Expected answer                              Preserve verified answer when available

Source IDs                                   Test + Attempt + Question

Syllabus path                                Subject/chapter/topic/subtopic where linked

Timestamp                                    Capture time

Screenshot behavior

For v1, 'screenshot' means an in-app question snapshot. This avoids unrestricted device capture and preserves the exact
learning context. The UI labels it as automatically captured evidence.

Failure handling

  If snapshot capture fails, the Error must still exist. The record should contain an evidence-unavailable state
  and allow later attachment/recovery. A failed image operation must never erase the learning event.

17. Reviews -- Scheduling and Queue

Reviews are correction activities generated from errors and driven by explicit outcomes.

Review record

Field                                        Purpose

Error ID                                     Source learning issue

Due time                                     When correction is expected

Method                                       Question/test/review type

Status                                       Open, due, overdue, completed, skipped

Schedule reason                              Why this interval was chosen

Review queue

The Reviews page has Due Now, Overdue, Open, Completed and History views. Due and overdue items should be
prioritized without hiding future work.

Starting a review

Open the source Error, show relevant context, then present a fresh verification question. The student should not simply
reread the original question and self-mark it correct.

Duplicate prevention

  The system should prevent multiple simultaneously active reviews for the same Error unless the review policy
  explicitly permits parallel verification.

18. Review Attempt and Review Outcome

A Review is complete only when the student produces a real outcome.

Review screen

Region                                       Content

Context                                      Error diagnosis + original evidence

Fresh question                               Verification item

Answer                                       Appropriate response control

Confidence                                   Optional correct/uncertain signal

Submit                                       Finalize review outcome

Outcome types

 · Correct + confident
 · Correct + uncertain
 · Incorrect
 · Skipped
 · Technical failure (not a learning outcome)

Outcome rules

Incorrect adds evidence and keeps the issue active. Correct outcomes advance the review policy. Correct-but-uncertain
should not automatically claim resolution. Skipped is not equivalent to success.

Technical failure

If the review cannot be completed because of a system error, do not record it as a learning failure. Preserve the review
and allow retry.

19. Review-to-Error Resolution Automation

This is the complete automated loop connecting Errors and Reviews.

Sequence

 · Error exists with Open state.
 · Review is scheduled.
 · Review becomes due.
 · Student starts fresh verification.
 · System records ReviewOutcome.
 · Incorrect  attach new evidence; keep/reopen Error.
 · Correct  advance resolution policy.
 · Qualifying evidence  Resolved.
 · Later recurrence  Reopened.
 · Dashboard, Insights and Notifications update from resulting events.

Example

A student repeatedly makes a sign error in quadratic equations. The first test captures the question snapshot and creates
an Error. The review produces another wrong answer, so the new evidence attaches to the same issue. A later review is
correct, but the product may require a second independent verification before resolution. If a future test is wrong again,
the Error reopens rather than starting with a blank history.

Explainability

  Every automated state change should be explainable in the UI: 'Reopened because a later verification was
  incorrect' or 'Resolved after two qualifying correct reviews.'

21. Planner -- Recovery, Missed Work and Recommendations

Missed work is a real state that should be recoverable rather than silently erased.

Missed task behavior

· Keep original task and planned date.

· Mark overdue/missed according to policy.

· Offer reschedule, split, shorten, deprioritize or leave unchanged.

· Record the recovery action separately from original history.

Recommendation engine

Repeated errors can produce a recommendation for targeted practice. Recommendations should be explainable and
distinguishable from confirmed tasks.

User control

Automatic task creation requires an explicit user-enabled policy. Otherwise the system presents a proposed action and
waits for confirmation.

Recovery example

Situation                                                       Recommendation

3 errors in one topic                                           Schedule targeted practice

Review overdue                                                  Open recovery choice

Large missed task                                               Split into smaller tasks

Weak topic with no planned work                                 Offer study block

23. Insights -- Performance Intelligence

Insights explains patterns from actual records and always preserves traceability.

Required insight families

Insight                                      Source

Accuracy by syllabus node                    Answers

Error recurrence                             ErrorEvidence

Review success                               ReviewOutcome

Resolved/reopened rate                       Error lifecycle

Evidence threshold

A small sample should not be presented as a strong conclusion. Insights can say 'limited evidence' and show the sample
size. The product should not use a single percentage as universal mastery.

Drill-down

Every important insight links to its supporting topic, errors, tests or attempts. A student can move from a weak-topic card
to the exact mistakes behind it.

Time windows

Support explicit windows such as recent 7/14/30 days and a custom range where practical. The chosen window is visible
in the UI.

26. Assistant -- Evidence-Grounded Product Behavior

The Assistant is a controlled interface to KRODEX's recorded learning state.

Allowed tasks

 · Explain an observed mistake.
 · Summarize recent performance.
 · Find unresolved errors.
 · Explain why a topic is prioritized.
 · Draft a study plan.

Fallback

If AI is unavailable, the application continues to support test submission, error capture, review scheduling and history
using deterministic/manual paths.

31. Security, Privacy and Evidence Storage Requirements

KRODEX stores educational performance information and captured question evidence; privacy must be part of the

Account isolation

 · Every protected record belongs to an authorized account/tenant context.
 · Server-side authorization is mandatory.
 · Client-side visibility is not a security boundary.
 · Object access must be checked on every protected mutation/read path.

Evidence privacy

External AI

Private student records should not be sent to external AI services unless the integration is explicitly configured and

Deletion/archive

Deletion semantics must be defined carefully so required historical evidence is not accidentally destroyed. Archive is
preferred for learning-domain objects with historical references.

33. AI Requirements, Guardrails and Deterministic Core

AI is an assistive layer; deterministic domain rules remain authoritative.

AI may assist with

 · Error classification suggestion.
 · Error explanation.
 · Question generation.
 · Performance summarization.
 · Study-plan drafting.
 · Recommendation wording.

AI may not independently

 · Invent a student's attempt.
 · Invent a syllabus node.
 · Declare an Error resolved.
 · Delete historical evidence.
 · Silently create durable tasks.
 · Present uncertainty as fact.

Action proposal pattern

For a mutation, the Assistant explains what it proposes, which records it would affect and why. The student confirms. The
server then executes the validated mutation.

AI failure mode

If the AI provider fails, core functionality falls back to deterministic/manual flows. AI availability is never allowed to become
a single point of failure for the learning loop.
