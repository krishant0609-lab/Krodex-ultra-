1. Technical Vision and Architecture Principles

Translate the PRD into a coherent system whose most important property is trustworthy state propagation.

Primary architecture

Use a modular web application with a typed client, typed server/API layer, relational database, object storage for evidence
snapshots, background job processing for asynchronous analysis, and an event/outbox mechanism for cross-module
projections.

Core principles

 · Server-authoritative domain state.
 · Transactional writes for high-risk learning events.
 · Idempotent commands for retries.
 · Immutable evidence and outcome history.
 · Explicit domain events for downstream projections.
 · AI isolated behind provider-neutral interfaces.
 · Read models optimized for dashboards without replacing source records.
 · Stable IDs and deep links for every durable entity.

Architectural boundary

  The browser can request, render and optimistically reflect safe UI state, but it cannot decide whether an Error is
  resolved, whether a Review is qualifying, or whether a submitted Attempt is final. Those decisions belong to
  server-side domain services.

Greenfield rule

Do not inherit assumptions from the deleted prototype. The implementation starts from the requirements in the PRD and
establishes contracts before screen-level coding.

5. API Style and Contract Standards

Define predictable APIs before implementing individual pages.

Command/query split

Use mutation endpoints for commands and read endpoints for queries. A command returns the resulting entity/version or
operation status; a query never mutates learning state.

 · DELETE is restricted and generally replaced by archive for historical learning objects.

6. Authentication, Authorization and Account Isolation

Security is a server-side architectural property.

Identity model

Every request resolves an authenticated account context. All protected records carry or inherit account ownership. Anonymous
access is limited to explicitly public resources, if any.

Authorization layers

· Route-level authentication.

· Resource ownership checks.

· Action-level policy checks.

· Mutation-specific authorization.

· Object-storage authorization through signed/private access paths.

Object authorization

For /errors/:id, for example, the service must load the error within the authenticated account scope before returning or mutating
it. Never fetch by ID alone and then check ownership in the browser.

Session security

Control                                                         Requirement

Cookies                                                         HttpOnly, Secure in production, appropriate SameSite

CSRF                                                            Protect cookie-authenticated mutations

Secrets                                                         Environment/secret manager, never source-controlled

Rate limiting                                                   Auth, AI and expensive endpoints

Audit                                                           Record sensitive state changes

Logging                                                         Never log private answer/evidence payloads by default

Tenant isolation

  A database query that omits account scope is a defect. Prefer repository methods that require accountId as a
  parameter so accidental cross-account queries become difficult to write.

7. Database Architecture and Transaction Boundaries

The database must preserve the exact learning history described by the PRD.

Transactional units

Transaction                                                     Atomic responsibilities

Submit Attempt                                                  Lock/check attempt  finalize  score  create eligible evidence  enqueue
                                                                downstream events

Complete Review                                                 Validate review  persist outcome  update lifecycle  schedule next review
                                                                 emit events

Create Test                                                     Persist definition  questions/provenance links  ready state

Archive Syllabus                                                Validate references  mark archived  emit event

Complete Task                                                   Validate status  record completion  emit event

Isolation

Use database transactions for state transitions that must not partially apply. Row-level locking or optimistic version checks
should prevent concurrent completion from producing contradictory lifecycle states.

Idempotency

High-risk commands accept an idempotency key or derive a stable command identity. A retried submission must return the
original result instead of creating a second Attempt or duplicate ErrorEvidence.

Outbox

Write domain events to an outbox table in the same transaction as the source mutation. A worker publishes/processes the
outbox after commit.

9. Automatic Error Capture Pipeline

Specify the P0 feature at service level, not just UI level.

Pipeline

Stage                                                           Technical responsibility

1. Submit                                                       Finalize Attempt exactly once

2. Score                                                        Evaluate answers using authoritative answer data

3. Identify                                                     Select incorrect eligible questions

4. Snapshot                                                     Create/store in-app question snapshot or mark unavailable

5. Link                                                         Create ErrorEvidence with source IDs

6. Group                                                        Match evidence to existing error pattern when policy supports it

Atomicity decision

The Attempt submission itself must not depend on successful AI classification. The submission and basic evidence record are
P0. Classification can be asynchronous while preserving a 'classification pending' state.

The recommended v1 implementation captures a deterministic in-app representation of the question/result region rather than
arbitrary device-wide screenshots. Store the resulting object privately and keep a metadata record in PostgreSQL.

Separate large binary evidence from relational metadata.

Storage model

11. Error Domain Model and Lifecycle Engine

Implement the Error state machine as a domain service.

State model

State        Allowed next states                                Trigger

OPEN         IN_REVIEW, ARCHIVED                                Review started / archive

IN_REVIEW    OPEN, RESOLVED                                     Incorrect / qualifying correct

RESOLVED     REOPENED, ARCHIVED                                 Later recurrence / archive

REOPENED     IN_REVIEW, ARCHIVED                                Review started / archive

ARCHIVED     --                                                 Terminal for active workflow

Transition service

A single ErrorLifecycleService should validate current state, required evidence, actor, policy and event source before changing
state. Controllers must never directly set status strings.

Concurrency

Use optimistic versioning or row locks around transitions. If two review submissions race, only one qualifying transition may win;
the other receives a safe conflict/retry response.

History

Every transition creates a lifecycle history record with fromState, toState, reason, actor, source event and timestamp.

13. Review Outcome and Resolution Rules

Make resolution deterministic and testable.

Outcome processing

ReviewOutcomeService validates that the Review is active, belongs to the Error, has not already been completed, and contains
a valid result. It then records the immutable outcome and asks ErrorLifecycleService for the next state.

Outcome rules

Outcome                                                         Lifecycle effect

Incorrect                                                       Error remains/returns OPEN; new evidence attached

Correct + uncertain                                             Record success signal; do not auto-resolve unless policy explicitly allows

Correct + confident                                             Advance policy; may resolve

Skipped                                                         No learning success; schedule according to policy

Technical failure                                               Do not alter learning lifecycle

Reopen

A later incorrect eligible answer against a resolved Error creates recurrence evidence and transitions it to REOPENED. Prior
resolution history remains untouched.

Idempotency

Completing the same Review twice with the same command ID returns the original outcome. A different conflicting outcome
against an already-completed review is rejected.

15. Attempt Persistence and Autosave

Autosave is a reliability feature, not a convenience.

Answer command

PATCH answer requests identify attemptId, questionId, answer payload and client command ID. The server validates that the
Attempt is still editable and stores the latest draft answer with version metadata.

Autosave strategy

Situation                                                       Behavior

Typing/selecting                                                Debounce client requests

Navigation                                                      Flush pending changes

Blur                                                            Attempt immediate save where useful

Network loss                                                    Queue locally until reconnect

Server conflict                                                 Refresh latest attempt version

Submitted attempt                                               Reject further mutation

Local recovery

Local browser recovery may preserve unsent draft data, but the UI must clearly distinguish local-unsynced state from
server-saved state.

Security

Do not place authoritative answer keys in client payloads before submission. The client receives only what is necessary to
render the question.

16. Attempt Submission Transaction

Submission is one of the highest-risk commands in KRODEX.

Submission algorithm

 · Load Attempt with account scope and lock/version check.
 · Reject if already submitted; return prior result for idempotent retry.
 · Validate required state.
 · Freeze answers.
 · Compute score using versioned scoring rules.
 · Persist submission timestamp/result.
 · Create eligible ErrorEvidence records or enqueue guaranteed processing.
 · Write outbox events.
 · Commit transaction.
 · Return final Attempt result.

Exactly-once illusion

Distributed systems rarely provide literal exactly-once execution everywhere. KRODEX achieves exactly-once domain effects
through unique constraints, idempotency keys, transactional state transitions and idempotent consumers.

Timeout behavior

If the client times out after the server commits, retrying the same command must return the committed result rather than create
another Attempt result.

Submission contract

  Once an Attempt is submitted, the server owns the final state. UI navigation, refreshes and duplicate clicks cannot
  revert it to editable.

21. Assistant Architecture and AI Guardrails

AI sits behind a controlled orchestration layer.

Assistant pipeline

 · Authenticate user.
 · Classify request intent.
 · Retrieve only authorized relevant records.
 · Minimize and structure evidence.
 · Call provider through adapter.
 · Validate structured output.
 · Attach source references.
 · Return answer/proposal.
 · Require confirmation for durable mutation.

Tool boundary

Expose narrow tools such as getError, getAttemptSummary, listDueReviews, getTopicMetrics and proposeTask. Do not give
the model raw database access.

Structured outputs

AI classification should return category, rationale, confidence and source IDs. The server validates category enums and source
ownership before storing it.

Mutation protocol

  Assistant proposals are not domain facts. A proposal becomes a mutation only after explicit confirmation or a
  previously enabled automation policy, and then passes through the same domain service used by the normal UI.

Provider failure

Timeouts, invalid JSON, quota errors and hallucinated IDs are treated as AI failures. Core deterministic workflows continue.

Notifications                                                   Eventual but prompt

Client caching

Cache safe GET responses with explicit invalidation. Mutation responses should update/invalidate affected caches. Never use
a cached Error status to authorize a transition.

Reconnect

On reconnect, the client reconciles local draft operations with server versions. Unsent answer commands are replayed with
command IDs; already-applied commands are acknowledged idempotently.

Stale UI

  A stale dashboard number is acceptable when clearly understood; a stale Error state used to decide whether a
  Review may resolve is not. Authorization and lifecycle checks always use server state.

24. Concurrency, Versioning and Race Conditions

Real users can click twice, use two tabs or lose connectivity.

Version strategy

Add integer version columns or updatedAt checks to mutable aggregates. Mutations include expected version where concurrent
editing matters.

Critical races

Race                                                            Protection

Double submit                                                   Idempotency key + submitted state

Two review completions                                          Review lock/version + unique completion

Archive during edit                                             Version check

Two task completions                                            Status transition constraint

Duplicate evidence job                                          Unique source occurrence key

Notification retry                                              Projection dedupe key

User-facing conflict

A conflict should be recoverable: refresh current state, explain what changed and preserve unsent local data when safe.

No hidden overwrites

  Never silently accept last-write-wins for immutable learning evidence. Mutable preferences may use simpler
  semantics; historical answers/outcomes may not.

26. Error Capture Screenshot Service -- Deep Technical Design

Specify the special feature down to implementation boundaries.

Recommended v1 approach

Render a canonical evidence snapshot from structured question/result data. The snapshot renderer receives a sanitized
EvidenceSnapshot DTO, not arbitrary DOM or privileged browser state. It outputs a deterministic image representation suitable

Snapshot DTO

Field                                                           Example

studentAnswer                                                   Recorded response

Security

Sanitize HTML/media references before rendering. Do not allow question content to execute scripts. Object storage keys are

If rendering is unavailable, persist the structured evidence and mark asset status Failed. A retry job can later create the image

27. Domain Rules for Automatic Error Grouping

Decide when repeated mistakes belong to one Error versus separate Errors.

Default principle

The safest v1 strategy is conservative grouping. Automatically link new evidence to an existing Error only when there is strong
deterministic identity, such as the same canonical question/skill issue, or a confirmed grouping rule.

Signals

 · Question ID/version.
 · Syllabus node.
 · Error category.
 · Normalized concept identifier where available.
 · Prior student-confirmed grouping.
 · AI suggestion only as non-authoritative evidence.

No unsafe merging

Two superficially similar wrong answers should not be merged merely because an AI model says they look similar. Create
separate evidence and offer a grouping proposal if confidence is insufficient.

Audit

  If grouping changes, store the reason and actor. Merging learning history must never erase the original occurrence
  records.

37. State Synchronization and Cross-Module Projections

Guarantee that one action becomes one coherent product state.

Submission propagation

Attempt submission is authoritative. It emits attempt.submitted and, after scoring/evidence processing, relevant error and
analysis events. Dashboard, Notifications and Insights consume projections rather than independently guessing that a test
happened.

Review propagation

Review outcome updates Review and Error in one transaction, then emits lifecycle events. Planner references the Review,
Dashboard reads due counts, Insights reads outcomes, Notifications reads the event.

Projection rebuild

Each read model must have a rebuild command or deterministic recomputation path. If a projector loses data, the source
records remain intact.

Freshness indicators

Where a projection can lag, internal observability tracks lag. User-facing UI should avoid presenting an old metric as exact
when its freshness guarantee is weaker.

38. Migration, Versioning and Backward Compatibility

Even a greenfield product will evolve after launch.

API versioning

Prefer additive changes first. Breaking changes require a versioned contract or coordinated deployment. Frontend and worker
consumers must not assume undocumented fields.

Event schema

Every event includes schemaVersion. Consumers tolerate additive fields and explicitly migrate when semantics change.

Question versioning

Submitted attempts reference the question version used. Future edits create new versions so historical evidence remains
reproducible.

Data migration rules

 · Never overwrite historical outcomes to 'fix' analytics.
 · Backfill with explicit migration provenance.
 · Run migrations on staging with production-like data volume.
 · Verify counts and foreign keys after migration.
 · Keep rollback/forward strategy documented.

Greenfield baseline

  The first production schema should already contain the fields needed for provenance, lifecycle history and
  idempotency. Do not postpone these as 'future improvements'.
